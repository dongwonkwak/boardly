# Boardly 소프트웨어 요구사항 명세서 (SRS)

## 1. 소개 (Introduction)

### 1.1 목적 (Purpose)

이 문서는 'Boardly' 프로젝트의 소프트웨어 요구사항을 상세히 기술하는 것을 목적으로 한다. 개발팀은 이 명세서를 기반으로 시스템을 설계, 구현 및 테스트한다.

### 1.2 범위 (Scope)

본 문서의 범위는 [PRD](PRD.md)에 명시된 P0(필수 핵심 기능 - MVP) 기능의 구현에 한정된다. 주요 기능은 사용자 인증, 워크스페이스, 보드, 리스트, 카드 관리, 카드 상세 기능 및 활동 내역 기능을 포함한다. 협업 기능, 알림, 개인 알림 센터는 P1 단계에서 구현 예정이다.

### 1.3 용어 정의 (Definitions)

- **RBAC (Role-Based Access Control)**: 역할 기반 접근 제어. 사용자에게 할당된 역할(Role)에 따라 시스템 자원에 대한 접근 권한(Permission)을 부여하는 방식.
- **워크스페이스 (Workspace)**: 보드들을 그룹화하는 최상위 컨테이너. 개인용(Personal)과 팀용(Team)으로 나뉜다.
- **보드 (Board)**: 실제 작업이 이루어지는 칸반 보드. 하나의 프로젝트 또는 업무 단위를 나타낸다.
- **API (Application Programming Interface)**: 프론트엔드와 백엔드 간의 통신을 위한 인터페이스.


## 2. 전체 시스템 설명 (Overall Description)

### 2.1 제품 개요 (Product Perspective)

Boardly는 단일 페이지 애플리케이션(SPA)으로 구성된 웹 서비스이다. 사용자는 웹 브라우저를 통해 서비스에 접근하며, 모든 데이터는 중앙 서버의 데이터베이스에 저장된다.

### 2.2 사용자 특징 (User Characteristics)

[PRD](PRD.md) 3절의 '타겟 사용자'와 동일하다.

### 2.3 제약 조건 (Constraints)

- **시스템 환경**: 시스템은 웹 브라우저 환경에서만 동작한다.
- **실시간 동기화**: WebSocket을 이용한 실시간 푸시(Push) 기반 동기화는 P1 단계에서 구현 예정이다. 현재 MVP에서는 페이지 새로고침을 통한 데이터 동기화를 제공한다.
- **언어 지원**: 초기 지원 언어는 한국어와 영어로 제한된다.
- **파일 저장**: 첨부파일 기능은 P1 단계에서 구현 예정이다. 현재 MVP에서는 파일 첨부 기능을 제공하지 않는다.


## 3. 시스템 기능 요구사항 (System Features)

### 3.1. 사용자 인증 (User Authentication)

회원가입은 이메일, 성(lastName), 이름(firstName), 비밀번호를 사용하여 진행하며, 로그인은 이메일과 비밀번호를 사용하여 수행한다. JWT 토큰 기반 인증을 사용하며, 비밀번호는 BCrypt 해시 처리하여 저장한다.

**사용자 스토리**: 가입한 사용자로서, 내 계정 정보를 최신으로 유지하고 보안을 위해 비밀번호를 변경하고 싶다.

**주요 기능**:
- 회원가입, 로그인, 로그아웃
- 프로필 조회 및 수정
- 비밀번호 변경
- 언어 설정 변경

**입력 유효성 (회원가입/비밀번호 변경)**:
- 비밀번호는 최소 8자 이상이어야 한다.
- 대문자 최소 1자, 소문자 최소 1자, 특수문자 최소 1자를 반드시 포함해야 한다.
- 성(lastName), 이름(firstName)은 1~50자, 한글 및 영문 알파벳만 허용한다.

### 3.2. 워크스페이스 (Workspace)

모든 보드를 그룹화하는 최상위 공간으로, **개인용(Personal)과 팀용(Team)**으로 구분된다. 사용자는 여러 워크스페이스를 생성하고 참여할 수 있다.

**사용자 스토리**: 사용자로서, 개인 프로젝트와 팀 프로젝트를 분리하여 관리하기 위해 별도의 워크스페이스를 만들고 싶다.

**주요 기능**:
- 워크스페이스 생성, 조회, 수정, 삭제
- Personal/Team 타입 구분
- 워크스페이스별 멤버 관리

#### 3.3.4 권한 적용 원칙

**최소 권한 원칙**: 사용자에게는 업무 수행에 필요한 최소한의 권한만 부여하며, 기본적으로는 제한적인 권한부터 시작하여 필요에 따라 점진적으로 확장합니다.

**상속 원칙**: 워크스페이스 소유자는 해당 워크스페이스 내 모든 보드에 대한 관리 권한을 가집니다. 보드 소유자는 해당 보드 내 모든 콘텐츠에 대한 관리 권한을 가집니다.

**격리 원칙**: 서로 다른 워크스페이스 간의 권한은 완전히 격리되며, 보드별로 독립적인 권한 관리가 가능합니다.

**초대 및 역할 설정 원칙**:
- **보드 초대**: 워크스페이스 OWNER 또는 해당 보드의 OWNER만 보드에 멤버를 초대할 수 있습니다.
- **워크스페이스 역할 고정**: 보드에 초대받은 사용자는 자동으로 워크스페이스 MEMBER 역할을 가집니다.
- **역할 상승 제한**: 보드 멤버는 워크스페이스 OWNER 역할로 상승할 수 없습니다.
- **보드 접근 제어**: 워크스페이스 OWNER는 모든 보드에 자동 접근 가능하며, 워크스페이스 MEMBER는 보드 생성 권한은 있지만 다른 사용자의 보드에는 초대받아야만 접근 가능합니다.

#### 3.3.5 권한 우선순위 규칙

권한 충돌 시 다음 우선순위에 따라 적용됩니다:

**🏆 1순위: 워크스페이스 OWNER**
- 모든 권한을 가짐 (어떤 보드 역할보다 우선)
- 자신의 워크스페이스 내 모든 보드에 대해 절대 권한
- 다른 사용자의 보드 역할을 변경하거나 보드를 삭제할 수 있음

**🥈 2순위: 보드별 권한**
- 해당 보드에서만 적용
- 워크스페이스 MEMBER이지만 특정 보드의 BOARD_ADMIN인 경우, 해당 보드 내에서는 BOARD_ADMIN 권한을 가짐
- 단, 워크스페이스 OWNER/ADMIN의 권한에는 미치지 못함

**🥉 3순위: 워크스페이스 MEMBER**
- 기본 권한만 (보드 생성, 할당된 보드 조회)
- 특별한 보드 권한이 없는 경우의 기본 권한

**권한 우선순위 적용 예시**

**시나리오 1: 워크스페이스 OWNER vs 보드 BOARD_ADMIN**
- **상황**: 워크스페이스 OWNER인 김PM이 개발팀장(보드 BOARD_ADMIN)이 만든 보드를 삭제하려고 함
- **결과**: 워크스페이스 OWNER 권한이 우선되어 보드 삭제 가능

**시나리오 2: 보드 BOARD_ADMIN vs 보드 BOARD_EDITOR**
- **상황**: 보드 BOARD_ADMIN인 개발팀장이 보드 BOARD_EDITOR인 개발자의 카드 삭제를 막으려고 함
- **결과**: 보드 BOARD_ADMIN 권한이 우선되어 카드 삭제 제한 가능

**시나리오 3: 워크스페이스 MEMBER vs 보드 BOARD_VIEWER**
- **상황**: 워크스페이스 MEMBER이지만 특정 보드의 BOARD_VIEWER인 사용자가 카드를 수정하려고 함
- **결과**: 보드 BOARD_VIEWER 권한이 우선되어 카드 수정 불가

#### 3.3.6 권한 검증 로직

**권한 검증 흐름**:
1. **토큰 검증**: JWT 토큰 유효성 및 만료 확인
2. **사용자 확인**: 토큰에서 사용자 ID 추출 및 활성 상태 확인
3. **워크스페이스 멤버십 확인**: 사용자가 해당 워크스페이스의 멤버인지 확인
4. **워크스페이스 역할 확인**: 사용자의 워크스페이스 역할 확인 (최우선)
5. **보드 멤버십 확인**: 해당하는 경우 보드 멤버십 확인
6. **보드 역할 확인**: 해당하는 경우 보드 역할 확인
7. **권한 우선순위 적용**: 워크스페이스 권한이 보드 권한보다 우선 적용
8. **최종 권한 검증**: 요청된 작업에 대한 최종 권한 확인
9. **권한 부여**: 모든 검증 통과 시 요청 처리

#### 3.4.1 멤버 초대 및 관리

**멤버 초대 및 관리**:
- **초대 방식**: 이메일 주소 또는 초대 링크를 통한 멤버 초대
- **초대 상태 관리**: PENDING, ACCEPTED, DECLINED, EXPIRED 상태 추적
- **역할 기반 초대**: 초대 시 워크스페이스/보드 역할 자동 설정
- **멤버 관리**: 멤버 제거, 역할 변경, 권한 관리

#### 3.4.2 멤버 초대 및 접근 제어

**초대 프로세스**:
- **초대 방식**: 이메일 주소 또는 초대 링크를 통한 초대
- **초대 상태**: PENDING, ACCEPTED, DECLINED, EXPIRED
- **초대 만료**: 7일 후 자동 만료
- **역할 설정**: 초대 시 기본 역할 설정 (워크스페이스 멤버, 보드 조회자)

**초대 및 역할 설정 규칙**:
- **보드 초대 권한**: 워크스페이스 OWNER 또는 해당 보드의 OWNER만 보드에 멤버를 초대할 수 있습니다.
- **워크스페이스 역할 자동 설정**: 보드에 초대받은 사용자는 자동으로 워크스페이스 MEMBER 역할을 가집니다.
- **역할 상승 제한**: 보드 멤버는 워크스페이스 OWNER 역할로 상승할 수 없습니다.
- **보드별 역할 할당**: 보드에 초대받을 때 OWNER, EDITOR, VIEWER 중 하나의 역할이 할당됩니다.

**접근 제어 메커니즘**:
- **API 레벨**: 각 엔드포인트에서 JWT 토큰 기반 사용자 인증
- **리소스 레벨**: 요청된 리소스에 대한 사용자 권한 검증
- **동적 권한**: 사용자의 워크스페이스/보드 멤버십 및 역할 확인
- **권한 상속**: 워크스페이스 소유자는 모든 하위 리소스에 대한 관리 권한


#### 3.4.3 실시간 동기화

**WebSocket 기반 실시간 동기화**:
- **연결 관리**: 사용자별 WebSocket 연결 및 재연결 처리
- **실시간 데이터 동기화**: 카드 이동, 수정, 댓글 추가 등의 즉시 반영
- **푸시 알림**: 새로운 활동, 멤버 초대, 마감일 알림 등

**협업 상태 표시**:
- **멤버 활동 상태**: 온라인/오프라인 상태 및 현재 작업 중인 보드 표시
- **실시간 커서**: 다른 사용자의 마우스 커서 위치 표시 (선택적)
- **편집 중 표시**: 현재 편집 중인 카드나 리스트에 대한 표시

**동시 편집 및 충돌 해결**:
- **동시 편집 지원**: 여러 사용자가 동시에 같은 보드에서 작업 가능
- **충돌 감지**: 동일한 리소스에 대한 동시 수정 시 충돌 감지
- **충돌 해결 메커니즘**: 
  - 마지막 수정 우선 (Last Write Wins)
  - 사용자에게 충돌 알림 및 수동 해결 옵션 제공
  - 편집 히스토리 추적을 통한 변경 사항 복구

#### 3.4.4 협업 알림 시스템

**실시간 알림**:
- **활동 알림**: 카드 생성/수정, 댓글 추가, 마감일 변경 등
- **멤버 알림**: 새로운 멤버 초대, 역할 변경, 멤버 제거 등
- **시스템 알림**: 보드 삭제, 워크스페이스 변경 등

**알림 설정**:
- **개인 알림 센터**: 사용자별 알림 관리 및 읽음 처리
- **알림 필터링**: 알림 유형별 필터링 및 설정
- **알림 전송**: 인앱 알림, 이메일 알림 (선택적)

### 3.5. 보드 (Board)

워크스페이스 내에 생성되는 프로젝트 단위의 작업 공간. 생성, 이름 변경, 삭제, 즐겨찾기 기능을 제공한다.

**사용자 스토리**: PM으로서, 새로운 프로젝트를 시작할 때 해당 프로젝트를 위한 보드를 생성하고 싶다.

**주요 기능**:
- 보드 생성, 조회, 수정, 삭제
- 보드 복제
- 즐겨찾기 관리
- 보드별 멤버 관리

### 3.6. 리스트 (List)

보드 내의 작업 단계 (예: To Do, Doing, Done). 생성, 이름 변경, 순서 변경(Drag & Drop), 삭제 기능을 제공한다.

**사용자 스토리**: 사용자로서, 내 업무 흐름에 맞게 '아이디어', '디자인 중', '개발 중', '완료' 같은 리스트를 만들고 싶다.

**주요 기능**:
- 리스트 생성, 조회, 수정, 삭제
- 리스트 순서 변경 (드래그 앤 드롭)
- 리스트 색상 설정

### 3.7. 카드 (Card) 및 카드 상세 기능

개별 업무 단위. 리스트 내에서 생성, 제목 변경, 순서 변경, 다른 리스트로 이동(Drag & Drop)이 가능하다. 카드를 클릭하면 상세 내용을 보고 편집할 수 있다.

**사용자 스토리**: 
- 팀원으로서, 내가 맡은 업무를 'To Do' 리스트에 카드로 생성하고 싶다.
- 사용자로서, 카드를 클릭하여 업무에 대한 상세 정보(설명, 마감일, 담당자)를 확인하고 싶다.

**기본 카드 기능**:
- 카드 생성, 조회, 수정, 삭제
- 카드 이동 (드래그 앤 드롭)
- 카드 복제

**카드 상세 기능**:
- **설명 (Description)**: 카드에 대한 상세 설명을 마크다운 형식으로 작성
  - *사용자 스토리*: 사용자로서, 업무에 대한 자세한 내용을 기록하고 싶다.
- **댓글 (Comments)**: 카드에 대해 팀원들과 의견 교환
  - *사용자 스토리*: 팀원들로서, 특정 업무에 대해 의견을 교환하고 싶다.
- **라벨 (Labels)**: '버그', '긴급', '디자인' 등 색상으로 카드 분류
  - *사용자 스토리*: 사용자로서, 업무의 성격이나 우선순위를 시각적으로 구분하고 싶다.
- **마감일 (Due Date)**: 카드의 마감 날짜와 시간 설정 및 완료 처리
  - *사용자 스토리*: 사용자로서, 업무의 마감일을 설정하고 기한을 놓치지 않도록 관리하고 싶다.
- **담당자 할당 (Assignees)**: P1 단계에서 구현 예정 (협업 기능)
  - *사용자 스토리*: PM으로서, 각 업무의 책임자를 명확히 지정하고 싶다.
- **첨부파일 (Attachments)**: P1 단계에서 구현 예정

### 3.8. 활동 내역 (Activity Feed)

보드 내에서 발생한 모든 활동을 시간순으로 기록하고 표시한다. 카드 생성/이동/수정, 댓글 추가, 담당자 할당 등의 활동이 포함된다.

**사용자 스토리**: 사용자로서, 보드에서 누가 언제 무엇을 했는지 추적하여 업무 진행 상황을 파악하고 싶다.

**참고**: 상세한 알림 기능은 3.4.4 협업 알림 시스템에서 다룹니다. 현재 MVP에서는 활동 내역을 통한 기본적인 활동 추적에 집중합니다.

## 5. 데이터베이스 요구사항 (Database Requirements)

### 5.1 논리적 데이터 모델 (ERD)

시스템은 다음과 같은 주요 엔티티와 관계를 가진다.

#### 주요 엔티티 (P0 - MVP)

- **Users**: 사용자 정보 (id, firstName, lastName, email, password, language, isActive, createdAt, updatedAt)
- **Workspaces**: 워크스페이스 정보 (id, name, description, type, owner_id, createdAt, updatedAt)
- **Boards**: 보드 정보 (id, name, description, isFavorite, workspace_id, createdAt, updatedAt)
- **Lists**: 리스트 정보 (id, name, position, color, board_id, createdAt, updatedAt)
- **Cards**: 카드 정보 (id, title, description, position, due_date, isCompleted, completedAt, list_id, createdAt, updatedAt)
- **Comments**: 댓글 정보 (id, content, card_id, user_id, createdAt, updatedAt)
- **Labels**: 라벨 정보 (id, name, color, board_id, createdAt, updatedAt)
- **Card_Labels**: 카드와 라벨의 관계 매핑 (card_id, label_id)
- **Activities**: 활동 로그 정보 (id, type, payload, user_id, board_id, timestamp)

#### P1 단계에서 추가될 엔티티

- **Workspace_Members**: 사용자와 워크스페이스의 관계 및 역할 매핑 (user_id, workspace_id, role, joined_at, invited_by, invited_at)
- **Board_Members**: 사용자와 보드의 관계 및 역할 매핑 (user_id, board_id, role, joined_at, invited_by, invited_at)
- **Card_Members**: 카드 담당자 매핑 (card_id, user_id) - 협업 기능
- **Notifications**: 알림 정보 (id, user_id, type, content, is_read, created_at, target_type, target_id)
- **Attachments**: 첨부파일 정보 (id, card_id, originalFileName, storedFilePath, fileSize, fileType, storageType, createdAt, uploader_id)
- **Checklists**: 체크리스트 정보 (id, card_id, title, position, createdAt, updatedAt)
- **Checklist_Items**: 체크리스트 항목 (id, checklist_id, content, isCompleted, position, createdAt, updatedAt)
- **Deletion_Requests**: 삭제 요청 정보 (id, type, target_id, scheduled_at, status, reason, created_by, created_at)
- **Data_Backups**: 데이터 백업 정보 (id, user_id, target_type, target_id, backup_data, download_url, expires_at, created_at)
- **WebSocket_Sessions**: 실시간 동기화를 위한 WebSocket 연결 관리 (id, user_id, session_id, connected_at, last_activity)
- **Collaboration_States**: 멤버들의 실시간 협업 상태 (id, user_id, board_id, current_action, last_activity)

#### 주요 관계 (P0 - MVP)
- User-Workspace (1:N) - 개인 사용자 중심 (owner_id)
- Workspace-Board (1:N)
- Board-List (1:N)
- List-Card (1:N)
- Board-Activity (1:N)
- Board-Label (1:N)
- Card-Label (N:M through Card_Labels)
- User-Comment (1:N) - 댓글 작성자

#### P1 단계에서 추가될 관계
- User-Workspace (N:M through Workspace_Members) - 협업 기능
- User-Board (N:M through Board_Members) - 협업 기능
- Card-Member (N:M through Card_Members) - 담당자 할당 (협업 기능)
- User-Notification (1:N) - 알림 기능
- Card-Attachment (1:N) - 첨부파일 기능
- Card-Checklist (1:N) - 체크리스트 기능
- Checklist-Checklist_Item (1:N) - 체크리스트 항목
- User-Deletion_Request (1:N) - 삭제 요청 관리
- User-Data_Backup (1:N) - 데이터 백업 관리
- User-WebSocket_Session (1:N) - 실시간 연결 관리
- User-Collaboration_State (1:N) - 협업 상태 관리
- Board-Collaboration_State (1:N) - 보드별 협업 상태

**권한 관리 세부사항**:
- **초대 관리**: 멤버 초대 시 이메일 발송 및 초대 상태 추적
- **역할 변경**: OWNER만 다른 멤버의 역할을 변경할 수 있음
- **권한 상속**: 워크스페이스 OWNER는 모든 보드에 대한 관리 권한을 가짐
- **접근 제어**: 각 API 엔드포인트에서 사용자의 역할에 따른 권한 검증

여기서 `role` 필드는 각각 `WorkspaceRole`(워크스페이스 소유자, 워크스페이스 멤버)과 `BoardRole`(보드 소유자, 보드 편집자, 보드 조회자) enum 값을 저장한다.

## 6. 비기능적 요구사항 (Non-Functional Requirements)

### 6.1. 성능 (Performance)
- 페이지 로딩 시간은 2초 이내
- 카드 이동 및 실시간 동기화는 0.5초 이내에 반응
- Lighthouse 성능 점수 85점 이상 달성

### 6.2. 사용성 (Usability)
- 별도의 튜토리얼 없이도 사용자가 핵심 기능을 쉽게 탐색하고 사용할 수 있어야 함
- 직관적인 드래그 앤 드롭 인터페이스
- 반응형 웹 디자인

### 6.3. 보안 (Security)
- 모든 사용자 비밀번호는 BCrypt와 같은 단방향 해시 함수를 사용하여 암호화
- SQL Injection, XSS, CSRF 등 기본적인 웹 보안 취약점에 대응
- JWT 토큰 기반 인증
- Rate Limiting 적용

### 6.4. 확장성 (Scalability)
- 최소 10만 명의 사용자와 수백만 개의 카드를 처리할 수 있도록 시스템 설계
- 인덱스 최적화를 통한 데이터베이스 성능 보장

### 6.5. 다국어 지원 (Internationalization - i18n)
- 시스템은 한국어와 영어를 지원한다.
- **프론트엔드**: React 환경에서 i18next 라이브러리 활용. 모든 UI 텍스트는 언어별 리소스 파일(예: `ko.json`, `en.json`)로 관리하여 동적으로 렌더링한다.
- **백엔드 (Spring Boot)**: API 응답 메시지 및 서버 측 유효성 검사 메시지는 Spring의 MessageSource를 활용하여 관리한다. 언어별 메시지는 `messages.properties`와 `ValidationMessages.properties` 파일에 정의한다. (예: `messages_ko.properties`, `ValidationMessages_en.properties`)
- 사용자의 기본 언어는 브라우저의 Accept-Language 헤더를 따르며, 사용자가 직접 UI에서 변경할 수 있는 옵션을 제공한다.
- 날짜/시간 포맷 현지화
- 동적 언어 전환 기능
