# Boardly 워크스페이스 설계 Architecture Decision Records (ADR)

## 개요

이 문서는 Boardly 프로젝트의 워크스페이스 관련 주요 아키텍처 결정사항들을 기록합니다. 각 ADR은 특정 문제에 대한 맥락, 결정, 근거, 그리고 결과를 포함합니다.

## ADR-001: Personal vs Team 워크스페이스 타입 분리 설계

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

Boardly는 개인 사용자와 팀 협업 모두를 지원하는 칸반 보드 서비스입니다. 사용자들은 개인적인 작업 관리와 팀 협업을 모두 필요로 하며, 이 두 영역은 서로 다른 접근 방식과 권한 관리가 필요합니다.

### 결정 (Decision)

워크스페이스를 **Personal**과 **Team** 두 가지 타입으로 분리하여 설계합니다.

- **Personal 워크스페이스**: 개인 전용, 멤버 초대 불가, 소유자만 접근
- **Team 워크스페이스**: 팀 협업용, 멤버 초대 가능, 보드 공개/비공개 설정 지원

### 고려된 대안 (Alternatives Considered)

1. **단일 워크스페이스 + 공개/비공개 설정만 사용**
   - 장점: 단순한 구조
   - 단점: 개인/팀 영역 구분 어려움, UI 복잡도 증가

2. **완전 분리된 개인/팀 계정**
   - 장점: 완전한 격리
   - 단점: 사용자가 두 개의 계정 관리 필요

3. **프로젝트 기반 그룹핑**
   - 장점: 유연성
   - 단점: 개념적 복잡도 증가

### 근거 (Rationale)

1. **명확한 사용 맥락 구분**
   - 개인 작업: 학습, 취미, 개인 업무 관리
   - 팀 작업: 회사 프로젝트, 팀 협업, 공유 작업

2. **권한 관리 단순화**
   - Personal: 권한 관리 불필요 (소유자만 접근)
   - Team: 체계적인 권한 관리 적용

3. **사용자 경험 최적화**
   - 개인 공간에서는 협업 기능 숨김으로 UI 단순화
   - 팀 공간에서는 협업 기능 강조

4. **보안 및 프라이버시**
   - 개인 프로젝트의 완전한 격리 보장
   - 실수로 개인 정보가 팀에 노출될 위험 제거

### 결과 (Consequences)

**긍정적 영향:**
- 사용자 경험 개선 (맥락에 맞는 기능 제공)
- 권한 관리 로직 단순화
- 개인 정보 보호 강화
- UI/UX 최적화 가능

**부정적 영향:**
- 데이터베이스 스키마 복잡도 증가
- 워크스페이스 간 보드 이동 기능 복잡화
- 개발 초기 구현 복잡도 증가

**완화 방안:**
- MVP에서는 보드 이동 기능 제외 (P1 단계로 연기)
- 워크스페이스 타입별 명확한 validation 규칙 적용

## ADR-002: BOARD_ONLY 사용자 타입 도입

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

Team 워크스페이스에서 외부 협력업체, 클라이언트, 임시 협업자 등을 특정 보드에만 제한적으로 초대해야 하는 요구사항이 있습니다. 이들에게 워크스페이스 전체 접근 권한을 주는 것은 보안상 부적절합니다.

### 결정 (Decision)

워크스페이스 멤버 타입에 **BOARD_ONLY** 타입을 도입합니다.

**BOARD_ONLY 사용자 특징:**
- 특정 보드에만 접근 가능
- 워크스페이스 정보 및 다른 보드 접근 불가
- 보드 생성 권한 없음
- 워크스페이스 멤버 목록에 표시되지 않음

### 고려된 대안 (Alternatives Considered)

1. **모든 사용자를 워크스페이스 멤버로 관리**
   - 장점: 단순한 구조
   - 단점: 보안 취약, 외부인이 내부 정보 접근 가능

2. **게스트 계정 시스템**
   - 장점: 임시 접근 지원
   - 단점: 회원가입 없는 접근의 보안 및 추적 문제

3. **별도의 외부 사용자 테이블**
   - 장점: 완전한 격리
   - 단점: 시스템 복잡도 대폭 증가

### 근거 (Rationale)

1. **보안 강화**
   - 외부 협력업체의 내부 정보 접근 차단
   - 최소 권한 원칙 적용 (필요한 보드만 접근)

2. **정보 격리**
   - 워크스페이스 멤버 목록, 다른 보드 정보 숨김
   - 회사 내부 구조 및 프로젝트 현황 보호

3. **유연한 협업**
   - 프로젝트별 외부 전문가 초대 가능
   - 클라이언트와의 제한적 협업 지원

4. **관리 효율성**
   - 프로젝트 종료 시 해당 보드에서만 제거
   - 워크스페이스 전체 권한 관리 불필요

### 결과 (Consequences)

**긍정적 영향:**
- 보안 수준 향상
- 외부 협업 활성화
- 정보 누출 위험 감소
- 클라이언트/협력업체 관리 용이

**부정적 영향:**
- 권한 관리 로직 복잡도 증가
- UI에서 사용자 타입별 다른 처리 필요
- 테스트 케이스 증가

**완화 방안:**
- 명확한 권한 검증 로직 구현
- 사용자 타입별 UI 분기 처리
- 충분한 테스트 시나리오 작성

## ADR-003: 워크스페이스 소유자 절대 권한 설계

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

워크스페이스 내에서 권한 충돌이 발생할 수 있는 상황들이 있습니다:
- 워크스페이스 OWNER vs 보드 OWNER
- 워크스페이스 멤버가 만든 비공개 보드에 대한 관리 권한
- 권한 체계의 우선순위 및 일관성

### 결정 (Decision)

**워크스페이스 OWNER에게 절대 권한을 부여**합니다.

워크스페이스 OWNER는:
- 워크스페이스 내 모든 보드(공개/비공개)에 대한 완전한 권한
- 보드별 역할에 관계없이 모든 작업 수행 가능
- 다른 사용자의 보드 역할 변경 및 보드 삭제 가능

### 고려된 대안 (Alternatives Considered)

1. **보드별 권한만 적용**
   - 장점: 보드 소유자의 자율성 보장
   - 단점: 워크스페이스 관리자의 통제력 부족

2. **상황별 권한 협상**
   - 장점: 유연한 권한 관리
   - 단점: 복잡한 로직, 예측 불가능한 동작

3. **민주적 권한 관리**
   - 장점: 공평한 권한 분배
   - 단점: 의사결정 지연, 관리 복잡도 증가

### 근거 (Rationale)

1. **명확한 책임 체계**
   - 워크스페이스에 대한 최종 책임자 명시
   - 권한 충돌 시 명확한 해결 방안 제공

2. **관리 효율성**
   - 조직 내 프로젝트 통합 관리 가능
   - 규정 위반 프로젝트나 콘텐츠 즉시 처리

3. **보안 및 컴플라이언스**
   - 조직 정책 위반 시 즉시 조치 가능
   - 외부 감사나 규제 요구사항 대응

4. **사용자 기대치 부합**
   - 조직 관리자가 모든 프로젝트를 통제할 수 있다는 일반적 기대
   - Slack, Microsoft Teams 등 유사 서비스와의 일관성

### 결과 (Consequences)

**긍정적 영향:**
- 권한 충돌 해결 메커니즘 단순화
- 조직 차원의 프로젝트 관리 강화
- 보안 사고 대응 능력 향상
- 권한 체계의 예측 가능성 증가

**부정적 영향:**
- 보드 소유자의 자율성 제한
- 워크스페이스 OWNER의 과도한 권한 집중
- 팀원들의 창의적 프로젝트 위축 가능성

**완화 방안:**
- 워크스페이스 OWNER의 권한 남용 방지 가이드라인 제공
- 개인 프로젝트는 Personal 워크스페이스 활용 권장
- 권한 행사 로그 기록 및 투명성 확보

## ADR-004: 공개 보드 자동 권한 부여 정책

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

Team 워크스페이스에서 공개 보드가 생성될 때, 기존 워크스페이스 멤버들에게 어떤 권한을 부여할지 결정해야 합니다. 매번 수동으로 초대하는 것은 비효율적이지만, 과도한 권한 부여는 보안 문제를 야기할 수 있습니다.

### 결정 (Decision)

**공개 보드 생성 시 워크스페이스 멤버들에게 자동으로 Editor 권한을 부여**합니다.

- 보드 생성자: OWNER 권한
- 기존 워크스페이스 멤버: 자동 EDITOR 권한
- BOARD_ONLY 사용자: 접근 불가 (개별 초대 필요)

### 고려된 대안 (Alternatives Considered)

1. **모든 접근을 개별 초대로 처리**
   - 장점: 명시적 권한 부여, 보안성 높음
   - 단점: 사용자 경험 저하, 관리 부담 증가

2. **Viewer 권한 자동 부여**
   - 장점: 보안성과 접근성의 균형
   - 단점: 협업 효율성 저하

3. **사용자별 기본 권한 설정**
   - 장점: 개인화된 권한 관리
   - 단점: 설정 복잡도 증가

### 근거 (Rationale)

1. **팀 협업 효율성**
   - 새 프로젝트 시작 시 즉시 협업 가능
   - 수동 초대 과정으로 인한 지연 제거

2. **공개 보드의 의미 명확화**
   - "공개"는 워크스페이스 멤버 모두가 참여 가능함을 의미
   - 사용자 기대치와 일치하는 동작

3. **권한 관리 단순화**
   - 복잡한 기본 권한 설정 메뉴 불필요
   - 직관적인 권한 체계

4. **확장성 고려**
   - 나중에 권한을 제한하는 것이 확장하는 것보다 쉬움
   - 개별적으로 권한 조정 가능

### 결과 (Consequences)

**긍정적 영향:**
- 팀 협업 장벽 제거
- 새 프로젝트 시작 시간 단축
- 사용자 경험 개선
- 권한 관리 부담 감소

**부정적 영향:**
- 의도치 않은 권한 부여 가능성
- 보안에 민감한 조직에서 우려 발생
- 권한 부여 알림 필요성

**완화 방안:**
- 보드 공개 설정 변경 시 명확한 안내 메시지 제공
- 보드별 멤버 권한 개별 조정 기능 제공
- 민감한 정보는 비공개 보드 사용 권장

## ADR-005: MVP에서 워크스페이스 간 보드 이동 기능 제외

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

사용자들이 Personal 워크스페이스에서 시작한 프로젝트를 Team 워크스페이스로 이동하거나, 그 반대의 경우가 필요할 수 있습니다. 하지만 이 기능은 권한 관리, 데이터 일관성, 멤버 관리 등에서 복잡한 문제들을 야기합니다.

### 결정 (Decision)

**MVP 단계에서는 워크스페이스 간 보드 이동 기능을 제외하고, P1 단계로 연기**합니다.

MVP에서는:
- 보드 복제 기능만 제공 (같은 워크스페이스 내)
- 워크스페이스 간 이동 없음
- 새 워크스페이스에서 새 보드 생성 권장

### 고려된 대안 (Alternatives Considered)

1. **MVP에 포함하여 완전한 기능 제공**
   - 장점: 사용자 요구사항 완전 충족
   - 단점: 개발 일정 지연, 복잡도 대폭 증가

2. **단순한 보드 복사로 이동 기능 대체**
   - 장점: 구현 간단
   - 단점: 활동 내역, 멤버 정보 손실

3. **관리자 전용 기능으로 제한**
   - 장점: 복잡도 일부 감소
   - 단점: 여전히 높은 구현 복잡도

### 근거 (Rationale)

1. **개발 복잡도 관리**
   - 권한 매핑 로직의 복잡성
   - Personal → Team 이동 시 멤버 권한 처리
   - Team → Personal 이동 시 기존 멤버 처리

2. **데이터 일관성 보장**
   - 활동 내역의 사용자 참조 문제
   - 댓글 작성자가 새 워크스페이스에 없는 경우
   - 파일 첨부 권한 및 소유권 문제

3. **MVP 목표 집중**
   - 핵심 칸반 보드 기능에 집중
   - 안정적인 기본 기능 우선 구현
   - 사용자 피드백 기반 개선

4. **위험 관리**
   - 복잡한 기능으로 인한 버그 위험 감소
   - MVP 출시 일정 준수

### 결과 (Consequences)

**긍정적 영향:**
- MVP 개발 일정 단축
- 핵심 기능의 안정성 향상
- 초기 사용자 피드백 빠른 수집 가능
- 개발 리소스의 효율적 활용

**부정적 영향:**
- 사용자 편의성 일부 제한
- 워크플로우 변경 시 불편함
- 기능 완성도 측면에서 아쉬움

**완화 방안:**
- 보드 복제 기능으로 부분적 해결
- P1 단계에서 우선순위 높게 개발 계획
- 사용자 가이드에서 워크스페이스 선택 기준 안내
- 향후 이동 기능 제공 예정임을 명시

## ADR-006: 공개/비공개 보드 설정을 Personal 워크스페이스에서 제외

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

Personal 워크스페이스는 개인 전용 공간으로 설계되었으나, 기술적으로 공개/비공개 보드 설정이 가능합니다. 이로 인해 사용자 혼란과 불필요한 UI 복잡도가 발생할 수 있습니다.

### 결정 (Decision)

**Personal 워크스페이스에서는 공개/비공개 보드 설정을 제외**합니다.

- Personal 워크스페이스의 모든 보드는 소유자만 접근 가능
- 보드 생성 시 공개 설정 옵션 표시하지 않음
- 데이터베이스의 `is_public` 값은 의미 없음 (항상 소유자만 접근)

### 고려된 대안 (Alternatives Considered)

1. **Personal에서도 공개/비공개 설정 제공**
   - 장점: 일관된 인터페이스
   - 단점: 의미 없는 기능, 사용자 혼란

2. **Personal 보드를 Team으로 공유하는 기능**
   - 장점: 유연성 제공
   - 단점: 워크스페이스 개념 혼재

### 근거 (Rationale)

1. **개념적 명확성**
   - Personal = 개인 전용이라는 명확한 정의
   - 사용자 혼란 방지

2. **UI 단순화**
   - 불필요한 설정 옵션 제거
   - 개인 사용에 최적화된 인터페이스

3. **보안 강화**
   - 실수로 개인 정보가 공개될 위험 제거

### 결과 (Consequences)

**긍정적 영향:**
- 사용자 경험 단순화
- 개인 정보 보호 강화
- 개발 복잡도 감소

**부정적 영향:**
- 기능적 제약 (향후 확장 시 고려 필요)

## ADR-007: 초대 시스템의 이메일/링크 이원화 설계

**날짜**: 2025-08-18
**상태**: 승인됨  
**결정자**: Boardly 개발팀  

### 맥락 (Context)

사용자를 워크스페이스나 보드에 초대하는 방법으로 여러 옵션이 있습니다. 각각의 장단점과 보안 고려사항이 다르기 때문에 적절한 방법을 선택해야 합니다.

### 결정 (Decision)

**이메일 초대와 링크 초대 두 가지 방식을 모두 지원**합니다.

**이메일 초대:**
- 특정 이메일 주소로 개인화된 초대
- 보안성 높음, 추적 가능

**링크 초대:**
- 7일간 유효한 초대 링크 생성
- 편의성 높음, 빠른 공유 가능

### 고려된 대안 (Alternatives Considered)

1. **이메일 초대만 지원**
   - 장점: 높은 보안성
   - 단점: 사용 편의성 저하

2. **링크 초대만 지원**
   - 장점: 사용 편의성
   - 단점: 보안 취약점

### 근거 (Rationale)

1. **사용 시나리오 다양성**
   - 공식적 초대: 이메일 사용
   - 빠른 공유: 링크 사용

2. **보안과 편의성 균형**
   - 상황에 맞는 적절한 방법 선택 가능

### 결과 (Consequences)

**긍정적 영향:**
- 사용자 선택권 제공
- 다양한 협업 시나리오 지원

**부정적 영향:**
- 구현 복잡도 증가
- 보안 정책 관리 복잡화
