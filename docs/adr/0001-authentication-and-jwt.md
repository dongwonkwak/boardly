# ADR 0001: JWT 기반 인증(Stateless)

- 상태: 승인됨
- 날짜: 2025-08-18

## 문맥(Context)
- 사용자는 워크스페이스/보드 리소스 접근을 위해 인증이 필요합니다.
- Spring Security 기반 `SecurityConfig`, `JwtConfig` 존재.
- 멀티테넌시는 `workspace_id` 기준의 권한 스코프를 요구하되, 사용자는 요청마다 활성 워크스페이스를 전환할 수 있습니다.
- 워크스페이스 관리에 대한 상세 내용은 [ADR 0002: 워크스페이스 관리 및 멀티테넌시](./0002-workspace-management.md)를 참조합니다.

## 결정(Decision)
API 인증 방식으로 Stateless JWT 액세스 토큰을 사용합니다.

- 액세스 토큰: 단수명(예: 15분).
  - `sub`: 사용자 ID(`user_id`)를 고정적으로 설정합니다.
  - `workspace_ids`(선택): 사용자가 속한 워크스페이스 ID 목록.
  - `roles_by_workspace`(선택): 워크스페이스별 역할/권한 맵 (OWNER, ADMIN, MEMBER, GUEST).
  - 활성 워크스페이스는 토큰에 포함하지 않습니다.
- 활성 워크스페이스 지정: 요청 헤더 `X-Workspace-Id` 또는 URL/path 파라미터로 전달합니다.
- 워크스페이스 전환: 토큰 재발급 없이 헤더만 변경하여 즉시 전환 가능합니다.
- 리프레시 토큰: httpOnly 쿠키 또는 안전 저장소, 사용 시 회전합니다.
- 토큰 검증: 서버 서명 검증으로 처리하며, 서버 세션 저장소는 사용하지 않습니다.

### 권한 검증 흐름
1. JWT 서명과 만료를 검증합니다.
2. 요청 헤더 `X-Workspace-Id`를 읽어 활성 워크스페이스를 결정합니다(엔드포인트가 워크스페이스 컨텍스트를 요구하는 경우).
3. 사용자가 해당 워크스페이스의 멤버인지 확인합니다(토큰의 `workspace_ids` 또는 저장소 조회).
4. 보드 관련 API인 경우 `X-Board-Id` 헤더를 확인하고, 해당 보드에 대한 권한을 데이터베이스에서 조회하여 검증합니다.
5. 엔드포인트 요구 권한에 대해 `roles_by_workspace` 등으로 인가를 검증합니다.
6. 실패 시 에러 카탈로그에 정의된 코드로 응답합니다.
   - 멤버가 아닌 경우: `WS-NOT_MEMBER`(403)
   - 보드 접근 권한 없음: `BOARD-ACCESS_DENIED`(403)
   - 권한 부족: `AUTH-INSUFFICIENT_SCOPE`(403)
   - 인증 실패: `AUTH-INVALID_TOKEN`/`AUTH-EXPIRED_TOKEN`(401)

### 개인보드 권한 검증 흐름
1. JWT 서명과 만료를 검증합니다.
2. 개인보드 관련 API인 경우 `X-Board-Id` 헤더를 확인합니다.
3. 해당 보드가 개인보드인지 확인합니다(보드 소유자 = 현재 사용자).
4. 개인보드 소유자인 경우 모든 권한을 허용합니다.
5. 실패 시 에러 카탈로그에 정의된 코드로 응답합니다.
   - 개인보드가 아닌 경우: `BOARD-NOT_PERSONAL`(403)
   - 소유자가 아닌 경우: `BOARD-ACCESS_DENIED`(403)

## 결과(Consequences)
- 장점:
  - 워크스페이스 전환 시 토큰 재발급 없이 헤더만 변경하면 되어 UX와 성능이 향상됩니다.
  - `sub` 의미가 표준에 부합하며, 감사/추적이 일관됩니다.
  - 보드별 세밀한 권한 제어가 가능하며, 권한 변경 시 즉시 반영됩니다.
  - 개인보드와 워크스페이스 보드를 통합적으로 관리할 수 있습니다.
- 단점:
  - 각 요청에서 `X-Workspace-Id` 헤더 누락/오류 처리 필요.
  - 보드별 권한 조회를 위한 추가 데이터베이스 I/O가 발생할 수 있습니다.
  - `X-Board-Id` 헤더 누락/오류 처리 필요.
- 요구사항:
  - 시계 오차 허용, 토큰 에러 i18n, 401/403 표준 응답.
  - 로깅에 `requestId`, `X-Workspace-Id`, `X-Board-Id` 포함.
  - 보드별 권한 조회 결과 캐싱 고려.
  - 워크스페이스 관리 관련 상세 요구사항은 [ADR 0002](./0002-workspace-management.md)를 참조합니다.
- 워크스페이스 역할 및 권한 상세 정의는 [워크스페이스 역할 정의 문서](../workspace-roles.md)를 참조합니다.

## 고려한 대안(Alternatives)
- 토큰에 현재 `workspace_id` 포함(기각): 워크스페이스 전환마다 토큰 재발급이 필요하여 UX와 보안(토큰 남용 표면)에서 불리함.
- Stateful 세션(Spring Session): 폐기 용이하나 저장소 의존과 결합 증가.
- OIDC 위임: 완결성 높으나 현재 범위에 과도.

## 후속 작업(Follow-ups)
- `SecurityConfig`/필터에서 `X-Workspace-Id` 및 `X-Board-Id` 추출 및 멤버십/권한 검증 로직 추가.
- API 가이드라인에 `X-Workspace-Id` 및 `X-Board-Id` 헤더 사용 규칙 명시(요청 필요 시 필수, 미지정 시 400 또는 기본 정책 정의).
- 에러 카탈로그(`docs/api/error_catalog.md`)에 관련 코드/메시지 키를 반영(이미 반영되어 있다면 최신화 유지).
- 리프레시 토큰 회전 및 재사용 탐지 구현.
- 보드별 권한 조회 결과 캐싱 전략 수립 및 구현.
- 개인보드와 워크스페이스 보드 구분 로직 구현.
- 워크스페이스 관리 관련 후속 작업은 [ADR 0002](./0002-workspace-management.md)를 참조합니다.
